## Carousel（§1.4 第五族，18/36，提交 `6622137`）

**移植源（Stage 1 最重数学移植）**：material-web 仅 token 导出 `_md-comp-carousel-item.scss`（34.0.21，无网页组件）；行为源 = **整个 Compose M3 carousel 包**（Carousel.kt 826 + Strategy.kt 685 + Keylines.kt 364 + KeylineList.kt ~500 + Arrangement.kt 277 行，约 2600 行），另抓官方 specs 页（headless Edge）与 **Compose 自己的单元测试 MultiBrowseTest.kt**（androidHostTest）做期望值锚定。

**关键数学（全部照抄）**：
- **Arrangement**：`fit` = small 先钳 [40,56] → large 精确解 `(avail − (s+m/2)*small)/(l+m/2)` → medium=(large+small)/2 → medium ±10% flex 回拉；`findLowestCostArrangement` 按 largeCounts(降序)×mediumCounts[1,0]×smallCounts[1] 遍历，cost=|target−large|*priority，cost 0 提前退出。**注意**：常见宽度下 cost 函数会选出「无 medium」排列（一大一小恰好填满）——这不是 bug，是 Compose 真行为；medium 槽位在滚动 step 中出现。
- **Keyline**：offset 轴按槽位自身 size 累计、unadjustedOffset 轴按 focal(large) size 累计（端到端滚动模型）；Start 对齐 pivotOffset=focalSize/2；cutoff=出界量。
- **σ 分段**：σ∈[startShift, endShift] 用 default；σ<startShift 在 startSteps 间插值（interpolation 1→0）、σ>endShift 在 endSteps 间插值（0→1）；shiftPoints 按每步位移占比。
- **item 定位（最关键坑）**：Compose 里 Pager 先把 placeable 放在流位置 `i*(L+s)−σ`，translation 是**相对修正**——Qt 折叠成一个公式：**wrapperX = interpolated.offset − largeSize/2 + 越界修正**（越界时 += (u−unadj)/size）。第一版直接用 translation 当 x 导致 item 反向漂移。
- maxScroll = large*N + spacing*(N−1) − available（注意测试里 Compose 自测用的 spacing*N 是它自己构造的数，不是组件公式）。

**Compose 测试锚定（强推荐手法）**：380/186/8 case 复现 `adjustsForItemSpacing` 期望——5 keylines、unadjusted=[−101,93,287,481,675]、large 不缩水 186、small=56 贴右；100/200 case 期望 4 keylines [anchor,L,S,anchor]；512/3 case 期望 surplus 削减后 5 keylines。有官方期望值打底，数学移植不再靠自洽断言。

**分歧登记**：spacing 8（spec）vs 0（Compose 默认）→ 按 spec 记录冲突；contentPadding shift 路径未移植（16px 归调用者边距）；hero/center-hero/uncontained/full-screen 策略未移植；无速度 fling（effects-default 弹簧 snap 到最近项边界）；item 内容鼠标穿透（carousel 独占拖拽，项交互归调用者）；zIndex 用 raise 顺序近似。

- **start/end 是逻辑 inline 边**：RTL 镜像（LayoutDirectionChange 时 update）；测试锚定。
- **垂直形态是 [compose]**（VerticalDivider，material-web 无）；thickness/color 参数覆盖照 Compose。

## Lists（§1.4 第七族，20/36，提交 `3b7e44a`）

**移植源**：material-web `tokens/versions/latest/sass/_md-comp-list.scss`（34.0.21，全量数值）+ `list/internal/_list.scss` + `list/internal/listitem/_list-item.scss`（两处 scss 硬编码）+ Compose `ListItem.kt` / `ListItemDefaults.kt` / `tokens/ListTokens.kt`（行为）+ m3.material.io lists specs（测量表）。**这是 §1.4 唯一 material-web 真实现了的族**，所以数值全来自导出，行为全来自 Compose。

**本次最关键的设计决定**：`MdListTokens::resolve` **原样上报导出值**，Standard/Expressive 的差异只体现在「行为」层。首版在 Standard 分支把 7 行 shape 覆写成 containerShape，导致 token 表在 Standard 下丢失 expressive 阶梯——**token 表是导出的镜像，"Standard 恒为直角" 是 `shapeFor()` 的规则**，不是 token 改写。这条对后续所有带风格变体的族都适用。

**关键事实**：
- **容器管选择与导航，条目只管画自己**：MdList 持有 roving tab stop、Arrow/Home/End、默认绕回（material-web `wrapNavigation ?? true`）、三种选择模式；对应 Compose 的 `selectable` 重载拆分 + material-web `ListController`。
- **行数是推导的**：有 overline 且有 supporting，或 supporting 折行 → 3 行；有其一 → 2 行；否则 1 行。56/72/88 是**下限**（内容高则撑破）。
- **形状阶梯 = 行为**：pressed > dragged > selected > focused > hovered > base；导出另有两行 disabled（未选中 extra-small、选中 large）插在 dragged 之后。**颜色行的顺序不同**（disabled 最先，照 Compose `ListItemColors.containerColor` 的 `!enabled -> … -> dragged -> … -> selected`）——`stateFor` 与 `shapeFor` 顺序不一致是**忠实的**，头文件里写明别"修"。
- **selected 的交互行把图标降到 on-surface**，label 仍是 on-secondary-container（导出的不对称，非笔误）。
- **`segmentedShapes(index,count)`**：首项上对角、末项下对角取列表 container.shape；单项**四条角全取**（count==1 是真实分段，不是"未分段"——首版守卫写 `count <= 1` 把它挡掉了）。
- **焦点指示环**：inward 变体 + 跟随容器圆角；thickness 来自 `focus.indicator.thickness`(3px)，间隙由 `focus.indicator.outline.offset`(-3px，CSS `outline-offset`) 推导为 0——`focusRingGap() = max(0, -offset - thickness)`，不是硬编码。`focusRingInset` 返回 0（环画在内部，无需父级留白，与 card 的 7.5px 外环相反）。

**分歧登记（6 条，全部入 porting-todo）**：between-space 12（token+Compose）vs 16（scss 硬编码）；trailing 右内边距 16（token）vs 24（spec）；8px 容器内边距**不是 token 行**（来自 _list.scss，resolve 刻意不查该键）；**拖拽 level4 阴影只承载不绘制**（条目容器即整个 widget 矩形，外溢阴影被 Qt 裁掉；Compose 靠浮层，MdList 是原位布局）；焦点环跟随容器圆角 vs material-web 硬编码 8px；material-web 整体 `opacity:0.38` vs 导出逐元素 opacity——**Compose 是第三种读法**（无 selectedDisabled 行，disabled 取 plain container，会让"选中且禁用"丢掉 secondary-container），本库按导出走。

**坑**：
- **`slots` 是 Qt 关键字宏**，作局部变量名会被展开成空 → 编译报 "expected unqualified-id before '='"。画廊页改用 `slotList`。
- **cleanup() 状态泄漏第四次重演**：`interactionStatesPaintLayers` 在 438 行的 QVERIFY 失败即中止槽，`setEnabled(false)` 没恢复，而 cleanup 没重置 enabled → 下一个槽 `selectionDrivesTheColours` 在「禁用+选中」下取到 `#9b94a6`（= on-surface 0.38 覆在 secondary-container 上）而非 `#e8def8`。**QCOMPARE/QVERIFY 失败 = 立即 return 出槽函数**——cleanup 必须穷尽重置。已把这条提升到项目 MEMORY.md。
- **QTest::mouseMove 在 Qt5 offscreen 下不合成 enter 事件** → hover 测试改用 `QEnterEvent(...)` + `QApplication::sendEvent`（TestMd3Card / TestMd3SplitButton 既有手法）；`sendEvent` 要非 const 的 QEvent*。
- **Qt5 offscreen 插件无字体库**：`drawText` 不产生任何墨迹（最暗像素 == surface）。像素级的"文字"断言必须**运行期探测**（先看静止态是否真有墨迹，没有就跳过），不能硬编码阈值；token 表断言不受影响。
- **库内没有任何颜色覆盖机制**（`MdCompTokenParse.h` 只有 length/shape，全库无 parseColor），所以画廊无法给条目换容器色 → 静止/悬停的 Expressive 形状在 surface 列表上**本就不可见**（material-web 亦然）。画廊演示因此全部靠 selected / dragged / disabled 态，并在文案里点明，避免被读成缺功能。

**验证手法（本次最有力的一条）**：画廊页 27 的 Standard/Expressive 对照片——**同内容同状态**，所以选中容器颜色/宽度/高度完全一致，**形状是唯一变量**。PIL 像素采样证明：两条选中带都是 1494×84 设备 px、色值均 `#e8def8`，而四角 1px 内侧采样一侧全为容器色（直角）、另一侧全为页面表面色（圆角）；另外核到分段间隙 3 设备 px（=2 逻辑 px）、拖拽态 `#dad4db`（on-surface 0.16 覆 surface）、选中禁用 `#9b94a6`（on-surface 0.38 覆 secondary-container）。
